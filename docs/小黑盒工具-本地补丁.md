## 1. 楼中楼完整性校验过严，连累整页读取

**现象**：`reply_comment` 用正文定位（`targetCommentContent`）时报「楼中楼数量不足，结果不完整」，明明评论就在那儿。

**根因**：平台返回的 `child_num` 把**已删除 / 已折叠**的回复也算进去了。实测：

```
984114643 「哪有养孩子让孩子赚钱的」  child_num=2  实际只回 1 条  has_more=false
```

`comments.py` 里这只检查一失败就 `raise ProtocolError`，整页 `read_thread` 全挂，按正文定位也跟着废。

**补丁**（`xhh_operator/comments.py`，约第 76 行）：

```python
if len(items) - 1 < int(items[0].get("child_num") or 0):
    # [本地补丁] 平台 child_num 含已删/折叠回复，校验失败不该拖垮整页
    group["_incomplete"] = True
```

**注意**：改完要重启 MCP 进程才生效（`pgrep -f "bin/xiaoheihe-cli mcp"` 拿到 pid，`kill`，host 会自动拉起）。

### 1b. 另外两处「读不完整就抛错」（2026-10-26 一起修的）

同一个毛病，`read_thread` 里还有两处：

```python
# 空页却标着还有下一页
if not page_groups and result.get("has_more_floors"):
```

## 4. 批量回复工具 `reply_many`（自己加的，不是原版）

`mcp_server.py` 里加了一个 `reply_many(postId, items, gap=12, dry_run=true)`：

- `items` 每项 `{"reply_id": "...", "root_id": "...", "text": "..."}`，顶层评论 `root_id` 等于 `reply_id`
- 按 `gap` 秒排队（最少 10），逐条提交，**全部完成后一次性返回**

```
reply_many(postId="195012420", items=[
  {"reply_id": "984140740", "text": "那就别查。"},
  {"reply_id": "984122558", "root_id": "984115428", "text": "什么算伟大，谁定？"}
], dry_run=false)
```

限制：一次最多 12 条（限流 10 秒一条 + 工具超时 180 秒）。改完要重启 MCP 进程
（`pgrep -f "bin/xiaoheihe-cli mcp"` 拿 pid → `kill`，host 会拉起来）。

命令行版在 `tools/xhh-reply-batch.py`，读 JSON 文件，适合特别长的单子。
## 5. 楼中楼不在 `/link/tree` 里

`/bbs/app/link/tree` 只给首页那几层楼、**不带全部楼中楼**，所以按正文找一条回复会扑空（正文还会被截断成「…」，`targetCommentContent` 更对不上）。

正确做法：先从 tree 拿到每栋楼的 `root_comment_id`，再逐个查楼中楼：

```python
params = {"link_id": pid, "root_comment_id": root, "limit": 20}
# 返回 result.comments + result.has_more + result.lastval，翻页把 lastval 带上
```

实测：`194802024` 只有 4 栋楼，但一条回复藏在 `983504865` 这栋的第 2 页里，tree 完全看不到。
## 6. 表情：正文里写，工具自动纠

正文里写 `[cube_xxx]` 会被扫描：

- 认得出（白名单里的中文名或英文名）→ 换成正确代码，比如 `[cube_狗头]` → `[cube_doge]`
- 认不出 → **当场报错**，还会给最接近的几个：「没有这个表情：[cube_狗] ，最接近的：狗头」

好处是写错的不会悄悄发出去变成一串文本。常见误写也补了别名：笑死→笑cry、笑哭→捂脸哭、摸头→摸摸头。

## 6. tags 被当 hashtag 传，报错却骂社区（2026-10-27）

**现象**：`publish_content(communities=["AI"], tags=["大肥鱼","数字生命","AI"])` 报
「社区或话题不存在，或同名结果不唯一；请核对准确名称」。照着字面查社区名，查了半天没毛病。

**根因**：`service.py` 的 `post_publish` 里

```python
hashtags=list(tags or ()),   # 参数名是 tags，语义是话题标签
```

MCP 工具对外叫 `tags`，传进 `resolve_selections` 就变成 `hashtags`。而
`selections.py` 对社区和话题标签共用一句报错文案，于是「数字生命」这类**不是话题标签**的词
搜不到，报出来却是「社区不存在」。`AI` 是社区不是标签，同样搜不到。

实测：`search --type topic AI` 能拿到 `AI | topic_id 806933`；`post_editor/topic_selection/search`
返回的 `search_type` 就是 `topic`、`name` 就是 `AI`——社区名一直是好的。

**补丁**（`xhh_operator/selections.py`，第 38 行附近）：

```python
if len(matches) != 1:
    label = "社区" if kind == "topic" else "话题标签"
    raise OperatorError(
        f"{label}搜不到或重名：{name}（精确匹配 {len(matches)} 个）", "selection"
    )
```

**绕法**：发帖时不传 `tags`，或只传**确认是话题标签**的词（实测「大肥鱼」能过）。

## 按正文定位回复：翻页重复楼层导致整条路失败（2026-10-27）

**症状**：`mcp__xhh__reply_comment` 用 `targetCommentContent` 定位时，报「评论分页未推进，停止读取；结果不完整」，明明那条评论就在帖子里。楼中楼尤其容易撞上。

**根因**（`xhh_operator/comments.py` 的 `read_thread`）：翻页时 `offset += len(page_groups)`，按楼层数推进；但平台 `/bbs/app/link/tree` 的分页不严格对齐，会把**已经读过的楼层再吐一遍**。原代码把「root 已见过」当成死循环：

```python
if not root or root in seen:
    raise ProtocolError("评论分页未推进，停止读取；结果不完整。")
```

于是整条 `read_thread` 失败，`locate_comment` 拿不到完整线程，按正文定位就废了。评论多的帖子、有楼中楼的帖子最先中招。

**补丁**：重复楼层跳过而不是报错。

```python
if not root:
    continue
if root in seen:
    # 平台翻页会重复吐回已读楼层，跳过继续翻
    continue
seen.add(root)
```

跳过后 `offset` 照常推进，仍然有 `max_pages=100` 兜底，不会死循环。

**生效方式**：改完必须重启 MCP 进程（`kill` 掉 `xiaoheihe-cli mcp`，dsh 会自动拉起），否则跑的还是旧代码。实测重启后同一条回复一次成功。

**顺带确认**：`list_messages` 里**有帖子 ID**，但 `get_post_detail` 返回的评论条目**不带 commentid**，所以「从提醒里拿帖子 ID 再去帖子里搜 ID」这条路走不通——只能靠正文定位，因此这个补丁是唯一的解法。

## 输出清洗补全：标题、用户名、话题描述（2026-10-27）

**背景**：正文和评论早就过 `clean_rich_text()`（剥 HTML、`@` 转「@名字（uid:数字）」、还原实体），但几个**外围字段**是裸读的，平台哪天在这些字段里塞标签就会原样吐给模型。

**补掉的五处**（`xhh_operator/service.py`）：

| 位置 | 字段 | 入口 |
|---|---|---|
| 通知行 | `title` | `list_notifications` |
| 消息行 | `link_title` | `list_messages` |
| 用户名 | `username` | `who_name`（所有带名字的行） |
| 用户搜索 | `rec_tag` | `search --type user` |
| 话题搜索 | `show_desc` | `search --type topic` |

统一套 `clean_rich_text`。改完同样要 **kill 掉 `xiaoheihe-cli mcp`** 让 dsh 重启才生效。

**实测（改后）**：`search` 847 字节、`search --type user` 1409、`--type topic` 1021、`feed` 1276，HTML 标签均为 0。默认路径的解构输出都带长度上限（通知正文 120 字、消息 70/100 字、摘要 90 字），不会因为长帖爆出几万字节。
